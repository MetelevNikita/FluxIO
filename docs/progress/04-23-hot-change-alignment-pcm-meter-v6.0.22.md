# 04.23 — HOT CHANGE после marker/recovery и PCM meter v6.0.22

Дата: 2026-08-14.

## Исправление HOT CHANGE

При старте с маркера или recovery media-service получает укороченный эфирный
Playlist, начинающийся с выбранного ролика. Electron при последующем изменении
LOGO/FX отправляет полный недельный Playlist. В v6.0.21 эти массивы сравнивались
по одинаковым индексам, поэтому первая строка ошибочно воспринималась как
удаление или перестановка текущего ролика.

В v6.0.22 media-service находит `currentItemId` в присланном UI Playlist и
выравнивает новый хвост от этого элемента. UI-строки до текущего ролика
игнорируются как уже сыгранная часть. Текущий ролик остаётся неизменным, а
правки следующего и более поздних роликов подготавливаются обычным HOT CHANGE.

## Исправление индикатора звука

FFmpeg `ametadata` писал RMS в stderr. На разных Windows builds эта служебная
запись могла отсутствовать, поэтому endpoint постоянно возвращал `null`.

Теперь media-service вычисляет RMS/dBFS напрямую из PCM s16le, который
audio-renderer передаёт в persistent encoder. Измерение подключается к
`audioBridge` только при активации ролика, поэтому заранее подготовленный
prefetched audio не попадает в эфирный индикатор. HTTP endpoint и частота UI
100 мс сохранены.

## Проверка

- unit test выравнивает `[уже сыгранный, текущий, следующий]` с фактическим
  эфирным `[текущий, следующий]`;
- unit test проверяет PCM ±0.5 full scale как приблизительно `-6.02 dBFS`;
- реальный FFmpeg/TSDuck UDP regression передаёт полный UI Playlist с лишним
  префиксом, пересобирает второй ролик и фиксирует ненулевой RMS во время эфира;
- оба ролика завершаются через один persistent encoder без остановки UDP.

## Проверка оператором

1. Запустить эфир с маркера в середине Current Playlist.
2. Во время эфира изменить LOGO или FX следующего ролика.
3. Убедиться, что появились `HOT CHANGE applied` и
   `HOT CHANGE armed for clip ...`, без ошибки remove/reorder.
4. На вкладке Broadcast проверить движение LEVEL и изменение числового dBFS.
