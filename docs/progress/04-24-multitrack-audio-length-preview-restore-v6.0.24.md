# 4.24. Длина многоязычных дорожек, таймлайн звука и превью после перезапуска (v6.0.24)

Статус: завершён 2026-08-18.

## Что было сломано

Эфир вставал при работе с роликами, у которых несколько звуковых дорожек с
разной длительностью или разными характеристиками исходных файлов.

Причина — в рендерере одной дорожки. `buildFfmpegClipAudioProducerCommand`
собирал граф вида

```text
[0:a:0]atrim=start=S:duration=D,asetpts=PTS-STARTPTS,aresample=…,aformat=…[aprogram]
```

`atrim` ограничивает дорожку сверху, но ничем не гарантирует её снизу. Файл
перевода короче ролика просто заканчивался раньше, и рендерер штатно завершался
с кодом 0, отдав меньше PCM, чем длится ролик. Измерено на чистом дереве:
файл `1.3 с / 44.1 kHz` при ролике 4 с давал 249 600 байт вместо 768 000.

Дальше срабатывала архитектура rolling playout. Постоянный program encoder
читает видео со stdin и по одному raw-PCM pipe на каждую дорожку программы
(`pipe:3`, `pipe:4`, …). Мультиплексор обязан чередовать все элементарные
потоки, поэтому молчащий вход останавливает выдачу целиком — не только свою
дорожку. Воспроизведение на модели encoder-а (видео + две дорожки, вторая
обрывается на второй секунде, выход UDP):

```text
без исправления            с исправлением
1s  10 KB                  1s  10 KB
2s  10 KB                  2s  10 KB
3s   1 KB   ← обрыв        3s  10 KB
4s   0 KB                  4s  11 KB
5s   0 KB                  5s  11 KB
6s   0 KB                  6s  10 KB
```

Выдача не возобновлялась: следующий ролик приходил в этот pipe со сдвигом, и
отставание только накапливалось. Отличие в характеристиках (частота дискретизации,
раскладка каналов) само по себе виновным не было — его снимают `aresample` и
`aformat`. Виновата именно незакреплённая длина.

Дополнительно `#completeClipProducer` требует завершения **всех** аудиорендереров
ролика, поэтому голодающий pipe задерживал ещё и переход к следующему ролику.

## Что сделано

### 1. Длина дорожки фиксируется по сэмплам

`clipAudioSampleCount(durationSeconds, sampleRate)` считает единое для всех
дорожек число сэмплов, и граф получает хвост

```text
…,apad=whole_len=N,atrim=end_sample=N,asetpts=PTS-STARTPTS[aprogram]
```

`apad` дотягивает короткий файл тишиной, `atrim=end_sample` срезает длинный по
сэмплу. Проверено на FFmpeg 9.0.1: файлы 1.3 с и 9 с, с `loudnorm` и без него, и
ветка `anullsrc` для ролика без перевода — все дают ровно 768 000 байт при
ролике 4 с / 48 kHz / stereo.

### 2. Страховка в supervisor

`ClipAudioRuntime` знает `expectedBytes` ролика и считает `writtenBytes`. Мост
теперь закрывает не `pipe`, а `#padClipAudio`: если рендерер всё-таки отдал
меньше (упал на середине, экзотический контейнер), недостача дописывается
тишиной с соблюдением backpressure, и только потом мост завершается. Событие
попадает в лог эфира с точностью до сотых секунды. Чистая функция
`clipAudioSilenceBytes` покрыта юнит-тестом: недостачу добиваем, лишнее не режем
— эти байты encoder уже забрал.

### 3. Таймлайн звука выровнен по кадрам превью

Раньше `.audio-track-lane` был гридом `132px 1fr`: подпись занимала отдельную
колонку и сдвигала полосы на 140 px вправо относительно кадров превью. Теперь
полоса занимает всю ширину панели — тот же левый край и та же ширина, что у
`.filmstrip-track`, — подпись лежит поверх заливки, а заливка растёт строго от
левого края вправо на долю ролика, покрытую реальным звуком.

Чтобы доля была настоящей, `audioTrackSchema` получил `durationSeconds`
(`null` — ffprobe промолчал), а `scanAudioTracks` измеряет длительность каждого
найденного файла: один `ffprobe` на файл, потолок параллелизма 8, ошибка не
роняет сканирование. Чистая функция `assetAudioLanes` раскладывает это по
полосам четырёх видов:

| вид | что значит |
|---|---|
| `original` | звук из самого видео, всегда во всю ширину |
| `present` | перевод не короче ролика |
| `partial` | перевод короче: заливка до границы, дальше — штриховка тишины, в подписи `short by N s` |
| `silent` | для этого ролика перевода нет, PID отдаёт тишину |

### 4. Превью переживают перезапуск приложения

`launch.mjs` гасит media-service вместе с Electron, а реестр проанализированных
роликов жил только в памяти процесса. После повторного запуска восстановленная
из БД сессия просила превью для «неизвестных» серверу файлов и получала 404 —
все картинки в интерфейсе гасли.

`MediaPreviewService` теперь знает `ffprobePath` и при первом обращении к
незнакомому файлу анализирует его заново: `#reregister` с дедупликацией по пути
и потолком в 4 одновременных `ffprobe` (восстановленное недельное расписание
запрашивает сотни превью сразу). Кэш картинок на диске переживает перезапуск как
и раньше, ключ включает размер и mtime файла. Тем же исправлением чинится и
Clip Preview после перезапуска — он ходил через тот же `#resolveRegistered`.
Путь кэша можно вынести из `tmpdir` через `GRUBER_MEDIA_CACHE_DIR`.

## Проверка

- `npm run typecheck` — чисто.
- `npm test` — 0 падений (media-server 72 pass / 5 skip, web 18, корневые 22).
- `GRUBER_RUN_FFMPEG_TESTS=1 npm test -w @gruber/media-server` — реальная сессия
  UDP CBR на двух роликах проходит; в неё добавлена проверка, что
  `MediaPreviewService` без единого `register()` отдаёт JPEG, а несуществующий
  файл по-прежнему даёт ошибку. Падает только `filter script opens embedded …`
  — известная несовместимость FFmpeg 9.x (`Unrecognized option
  'filter_complex_script'`), не регрессия.

## Что осталось

- `audioTrackSchema.streamIndex` по-прежнему игнорируется: рендерер жёстко берёт
  `[0:a:0]`. Для файла перевода с несколькими дорожками внутри это неверно.
- Дорожки, объявленные в расписании через `insertAudioTrack_{язык}`, не
  превращаются в `MediaAsset.audioTracks`, поэтому в таймлайне их не видно —
  полосы строятся только по результату сканирования папки.
